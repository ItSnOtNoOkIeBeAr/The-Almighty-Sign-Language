# DECISIONS

One line per non-obvious choice: what and why.

## Phase 0
- **Repo location `C:\dev\almighty-sign-language`**: the user's home path contains a space, which breaks some CUDA/CMake tooling (spec rule 8).
- **VS dev environment loaded by script, not by reopening VS Code**: `cl` and `cmake` are not on the default PATH. Scripts call `vcvars64.bat` (located via the VS install path) so builds work from any terminal. Verified: `cl` 19.42.34436, CMake 3.29.5-msvc4, Ninja from VS.
- **Extra error codes in PROTOCOL.md** (`bad_type`, `too_short`, `bad_version`, `empty_payload`, `internal`): the spec lists `bad_magic|too_large|decode_failed|...`; these fill in the `...` so both servers and the conformance test agree on exact codes.
- **End-of-stream semantics**: spec defines the flag but not the behaviour. Chosen: an EOS message with an empty payload gets no result and resets that connection's decision state.
- **Max message size 2 MB = 2 097 152 bytes, header included**.

## Phase 1
- **vcpkg baseline `857036234d15fbed8f30fed66e898d7725446c0c`** (vcpkg tool 2026-09-26): pinned for reproducible builds. Installed: ixwebsocket 12.0.1, nlohmann-json, spdlog 1.17.0 (fmt 12.2.0), gtest. Triplet `x64-windows`.
- **ixwebsocket without SSL** (`default-features: false`): TLS terminates in `cloudflared` on the same PC, and the server binds to 127.0.0.1 only, so mbedtls would be dead weight.
- **ixwebsocket kept over Boost.Beast, with a custom server subclass**: `ix::HttpServer` is `final` and upgrades WebSocket requests *without* calling the HTTP callback (verified in `IXHttpServer.cpp:95-108`), so it cannot do "401 before upgrade". Instead we subclass `ix::WebSocketServer`, override its virtual `handleConnection`, call `ix::Http::parseRequest`, answer `/health` and 401 ourselves, and call the protected `handleUpgrade(socket, state, request)` only for authorised `/ws` upgrades. Small, contained, and no second networking library.
- **TensorRT 10.16.1.11 (not 11)**: newest 10.x GA; the zip for CUDA 13.0-13.2 matches the 13.2 toolkit and contains sm_120 builder resources. TensorRT 11 is a new major version with possible API changes, so it is held back unless 10.x fails.
- **ORT CUDA DLLs registered by `training/ort_cuda.py`**: onnxruntime-gpu 1.31 needs `cublasLt64_13.dll` (in `CUDA\v13.2\bin\x64`, not on PATH) and cuDNN 9 (taken from torch's lib folder, a CUDA 12.8 build, which works with ORT's CUDA 13 provider here). Without them ORT silently used CPU, so `make_session()` raises unless CUDAExecutionProvider is first.
- **No separate cuDNN install**: TensorRT 10 does not need it, and torch's copy covers ORT.

## Phase 2
- **Port 127.0.0.1:8765 for both servers** (user request, avoids clashes with other projects). BUILD_SPEC.md, PROTOCOL.md and `server.json` updated; port verified free first.
- **Fallback 401 via a pure-ASGI wrapper (`AuthWS`)**: FastAPI closing a WebSocket before `accept` yields HTTP 403, not the required 401. The wrapper answers the `websocket.http.response` denial extension. uvicorn then logs a false "ASGI callable returned without completing handshake" ERROR; that one message is filtered (verified in uvicorn's `websockets_sansio_impl.py`: denial never sets `handshake_complete`, and `send_500_response` returns early).
- **uvicorn `ws_max_size` = 16 MiB, app limit 2 MiB**: a frame over the limit must get a `too_large` reply and keep the connection (PROTOCOL.md); uvicorn's own limit would instead close the socket (code 1009). Anything over 16 MiB still closes the socket, which is acceptable for a clearly abusive client.
- **Placeholder shapes**: temporal model `[1, 45, 96] -> [1, 8]`; the 96 = 8x12 grayscale thumbnail of the dummy keypoint step. Real F is decided in Phase 3/7; `window.feature_dim` in `server.json` must change with it.
- **EMA smoothing in the fallback (alpha 0.5)** and `run_every_k_frames` are read from `server.json` so the C++ server can share them.
- **Client uses `websockets.sync` + threads** (sender+reconnect thread, one receiver thread per connection, capture/display in the main thread): no asyncio in the laptop client, fewer moving parts, and a slow network cannot freeze the preview.
- **Recorder samples like live streaming** (newest camera frame at each 1/fps tick, via a capture thread, repeats allowed): the first version waited for each camera frame and stretched clips to 4.2 s on this dim ~12 fps webcam while `meta.json` said 15 fps. Same `prepare_frame` + `encode_jpeg` as the live path.
- **Extra `meta.json` key `unique_camera_frames`** (beyond spec section 6): lets training later drop clips recorded with a starved camera. The recorder also prints a warning below 80% distinct frames.
- **Token handling**: generated with `RandomNumberGenerator` (32 bytes, base64url, 43 chars), stored with `setx` as a user env var, read back by length/equality only. Never written to a file or echoed. Read it on this PC with `[Environment]::GetEnvironmentVariable('SIGNLANG_TOKEN','User')`.
- **Camera on this PC**: A4tech PC Camera = index 0, 640x480 only. Spec default stays 1280x720 in `client/config.json`; tests here override with `--width 640 --height 480`. Training data must be recorded at one consistent resolution, to be settled before Phase 7.
- **Public hostname `signlang.dheynorlanda.me`** (user's Cloudflare zone, published application route to `http://localhost:8765`). `client/config.json` now defaults to `wss://signlang.dheynorlanda.me/ws`; local tests pass `--url ws://127.0.0.1:8765/ws`. The hostname is not a secret; the tunnel token and `SIGNLANG_TOKEN` are, and are in no file.
- **Conformance health check sends an explicit User-Agent**: Cloudflare blocks the default `Python-urllib` signature (error 1010). Cloudflare settings were left untouched.

## Phase 2 follow-up
- **Client flow control (`max_inflight`, default 3)**: the server's latest-only slot cannot stop a backlog that builds in the laptop's own send buffer / Wi-Fi queue. The client therefore skips a send while more than 3 frames are unanswered (answers include per-frame errors; a 2 s timeout prevents deadlock). Proven with a throttled link: RTT 8.6 s -> 0.25 s. Cost: on a slow link the effective fps drops instead of latency growing, which is the right trade for live recognition.
- **Stream settings are a deliberate choice, not a default**: 1280x720 q80 at 15 fps needs ~10 Mbit/s up, more than this laptop's Wi-Fi gives. Candidates measured: 640x360 q70 (22 KB/frame). Decide together with Phase 3 (hand detail needed by the keypoint model) before recording training data.
- **Chosen live stream settings: 640x360, JPEG q70, 10 fps, max_inflight 3** (user said "just do what's best"). Why: ~22 KB/frame x 10 fps = ~1.8 Mbit/s fits this laptop's Wi-Fi (8 fps measured flat at ~140 ms); 15 fps at the same size sat at 500-700 ms; 1280x720 q80 collapsed. Fall back to 8 fps if the laptop shows p50 > 200 ms. Risk: less hand detail for the keypoint model; Phase 3 must test on frames of exactly this size.
- **Clip length = 3 s at the live fps (30 frames at 10 fps)**, per spec section 6 ("3-second clip at the live FPS"). This differs from the spec's example `000..044`, which assumed 15 fps. The 45-frame temporal window in `server.json` is a placeholder until Phase 7 sets it from the real clip length (or resamples clips).
- **Stream and clips changed to 640x480 (4:3), q70, 10 fps, max_inflight 3** (user: "fix the 4:3"): this laptop's camera only delivers 640x480, and `prepare_frame` squashed it to 640x360 (vertical scale 0.75, faces/hands distorted, and clips would have carried it). Native size needs no resize. Why not crop to 16:9: it cuts hands/face at the frame edge. Cost: ~30 KB/frame x 10 fps = ~2.4 Mbit/s. Measured over the tunnel on the laptop (20 s each, config values): p50 446.6 / 135.5 / 131.6 / 464.8 ms across four runs. Bimodal, not growing: good runs skipped 2-3 frames, bad runs sat flat at ~450 ms and skipped ~77. 480x360 gave 437 ms (10 fps) and 239 ms (8 fps), so size is not the driver; the Wi-Fi link is. The 200 ms rule is met in about half the runs. Revisit when the laptop is on a better link (5 GHz, closer, cable). Phase 3 must test on 640x480 frames.
- **`run.ps1` no longer hard-codes size/duration for the client**: `client\config.json` controls resolution, fps and quality; extra arguments pass through (`.\run.ps1 headless --duration 20`).

## Phase 3: keypoint model selection (2026-11-18) - AWAITING USER APPROVAL
**Recommendation:** primary = RTMW-x(l) 384x288 (`rtmw-dw-x-l_simcc-cocktail14_270e-384x288`) on the **full frame (no detector)**, TensorRT FP16, GPU 3.9 ms p50 / 5.2 ms p95. Fallback ("safe mode") = RTMW-l-m 256x192 (`rtmw-dw-l-m_simcc-cocktail14_270e-256x192`), 3.2 ms p50. An optional person detector (YOLOX-tiny, +2.6 ms) only if the live check shows the signer too small. DWPose stays a documented backup, not chosen. One model in the stage (spec: fewest wins); its output is 133 SimCC keypoints (body 0-16, feet 17-22, face 23-90, left hand 91-111, right hand 112-132).

**Why, and how sure:** accuracy differences between candidates are NOT measurable here: the dataset has no hand labels, so only proxies exist (below), and on those all five models are within noise. The pick rests on (1) the highest input resolution (384x288 gives small hands the most pixels), (2) the best FP16 stability (0.16% of keypoints move >5 px vs ORT; DWPose-l 3.6%), (3) 3.9 ms leaves most of the ~12 ms keypoint budget, (4) a detector adds a model, an NMS graph and 2.6-3.5 ms, and removing it made no measurable difference on the proxies. The choice is cheap to reverse: every candidate has the same 133-keypoint SimCC interface and pre/post-processing (only the input size differs), so Phase 7 can compare end-to-end sign accuracy. A temporal model trained on one extractor's keypoints must be run with that extractor, so "safe mode" needs its own training pass or augmentation (Phase 7/9).

**Exact preprocessing** (from each model's `pipeline.json`, cross-checked with rtmlib 0.0.16; reference code `training/rtmw_ref.py`):
- Pose: bbox -> center = box middle, scale = box size x 1.25; fix the aspect to the model input W/H (widen height or width); affine warp (mmpose 3-point: center, center + (0, -scale_w/2), and its 90-degree rotation) with bilinear sampling and a zero border to W x H; RGB; `(x - [123.675, 116.28, 103.53]) / [58.395, 57.12, 57.375]` on 0-255 values; NCHW float32. Input sizes (W x H): 288x384 for the 384x288 models, 192x256 for the 256x192 models. `pipeline.json` lists image_size 192x256 even for the 384 export (stale; the real size is the ONNX input). Full-frame box = [0, 0, 640, 480].
- Decode: `simcc_x [133, 2W]`, `simcc_y [133, 2H]` -> argmax per axis / 2 (split ratio 2.0, no DARK) -> `/ input_size * scale + center - scale/2`; score = mean of the two peak values (as rtmlib); coordinates set to -1 when score <= 0.
- Detector (YOLOX, decode + NMS inside the ONNX): keep-ratio resize into 640x640 (416 for tiny), pad 114 at bottom/right, BGR, mean 0 / std 1 (raw 0-255 floats), NCHW. Output `dets [1,N,5]` (x1, y1, x2, y2, score) and `labels`; boxes / resize ratio. mmdeploy NMS iou 0.65, score threshold 0.01 (we take the best label-0 box >= 0.5).
- For Phase 5: fused kernel = affine crop + RGB + normalize written straight into the engine input; decode kernel = SimCC argmax.

## Phase 7: training (SignNet on ASL Citizen keypoints)
- **Keypoints:** every clip -> 10 fps / 640x480 / JPEG q70 via `client/common.encode_jpeg` -> full-frame box -> primary AND fallback RTMW model (ORT CUDA), cached in `data/public/asl_citizen/keypoints/` (4,826 clips, 138,521 frames, ~35 min; 4 CPU threads decode while the GPU runs). `training/extract_keypoints.py`.
- **Features (`training/signfeat.py`, shared by training and the server, so they cannot drift):** 57 points (shoulders, elbows, wrists, nose, 4 eyebrow + 4 mouth points, 21 + 21 hand points) normalised per 30-frame window by the median mid-shoulder and shoulder width; plus velocities and 5 flags = 233 features per frame, 30 frames (3 s at 10 fps). Mirroring is off (spec): a few left-handed signers are not modelled specially.
- **Hand presence needed two levels.** The first version (hand keypoints >= a score threshold) called ~75% of resting frames "hand present" (RTMW hallucinates confident hands below the frame), so the active segment of a clip was the whole clip and the idle gate could never close. Fitted on signing-vs-resting frames of all clips: **strict** presence = >= 15/21 points above a stricter per-model score (`HAND_PRESENT_THR`: 3.44 for RTMW-x 384, 0.56 for RTMW-l-m 256) AND >= 90% of the points inside the frame (resting-frame false positives ~2% per hand). Strict flags drive the idle gate and the active-segment detection; the loose flags still decide which hand points are kept as features (strict alone throws away real but low-confidence hands).
- **Windows:** a clip's active segment is the first to last run of >= 2 strict-hand frames (median 1.2 s; 77-95% of clips have resting frames before/after). Words: the sign placed anywhere in the window keeping >= ~70% of it, speed 0.8-1.2x, nearest-frame sampling, holding the resting frame at the ends (like the live stream). `none` = other-gloss clips (150 glosses, 4,575 clips) + resting windows from the start/end of ALL clips, per epoch exactly 3x the largest word class (half each); inverse-frequency class weights, label smoothing 0.05.
- **Compound windows (important):** 35% of word windows hold an EARLIER sign (any word/other clip) followed by the target sign; the label is the later sign. Without them the model, which had only ever seen one sign per window, kept predicting the first word of a sentence while the second was signed (sentences 0% in replay); with them sentences work at 15-24%. A further variant (15% `none` windows with an earlier sign and only the first frames of a new one) made false triggers and sentences WORSE (e.g. false triggers 6.5% -> 13%) and was switched off (`NEW_SIGN_NONE = 0`).
- **Model (`training/sign_model.py`):** Linear + LayerNorm embedding (233 -> 192), 2 residual Conv1D layers (k 5, BatchNorm), learned positions, 3 pre-LN Transformer blocks (4 heads, FF 384, dropout 0.15, plain matmul attention so TensorRT parses it), mean+max pooling, linear head; **1,315,015 parameters**. AdamW lr 1e-3 (OneCycle), wd 1e-2, bf16 autocast, grad clip 1, GPU-resident data and GPU augmentation: rotation +-10 deg, scale 0.9-1.1, shift +-0.1 shoulder widths, noise 0.01, 10% frame drops (repeat previous), a missing hand for 20-60% of the frames (12% per hand), speed 0.8-1.2x, time shift. ~1 min per seed on the RTX 5060 Ti.
- **Split discipline:** train on `train` (35 signers), early stopping (patience 15) and seed/decision selection on `val` (6 signers) only, **report on `test` (11 signers) only**; nothing was ever chosen on test. 8 seeds per keypoint model.
- **Primary vs fallback keypoints, on val:** window macro-F1 mean over 8 seeds: RTMW-l-m 256x192 **0.889** (0.865-0.924) vs RTMW-x 384x288 **0.862** (0.820-0.889). End-to-end replay score on val (word_correct - 2 x false_trigger + sentence_correct): per-seed mean RTMW-x 0.875 (0.82-0.97) vs RTMW-l-m 0.73 (0.59-1.13); best seed 0.965 vs 1.125. Test (reporting only): RTMW-x better on words (71% vs 68%), false triggers (3.7% vs 6.5%) and sentences (24% vs 15%). **Mixed evidence, no clear val winner**, so the approved primary stays the server default and the 256x192 model is trained and exported as the `fallback` profile (`python server/fallback/fallback_server.py --profile fallback`). The user asked for the val winner: by window macro-F1 alone that is RTMW-l-m 256x192 (switch = one flag, both engines are built).
- **Selected checkpoints:** seed chosen by end-to-end val replay score (`training/replay_eval.py --tune`, which also grids commit_threshold {0.5-0.8}, M {2,3,4}, EMA alpha {0.5,0.7} on val): primary seed 2 -> threshold 0.5, M 4, alpha 0.7; fallback seed 2 -> threshold 0.5, M 3, alpha 0.7 (per-profile override in `server.json`).
- **ONNX/TensorRT:** fixed `[1,30,233] -> [1,7]`, opset 17. ONNX vs PyTorch on the 533 real test windows: **max |logit diff| 9e-6** (exact FP32 ORT-CUDA), argmax agreement 100%. The ORT CUDA provider's default TF32 matmuls move logits by 3.9e-3 (primary) / 7.4e-3 (fallback): found because my first 1e-3 check failed; confirmed with ORT-CPU (5e-6) and `use_tf32=0` (9e-6); the tolerance stayed strict, and the temporal session now runs with TF32 off (`ort_cuda.make_session(..., tf32=False)`). TensorRT FP16 engines (`server/models/temporal_*.engine`, 4.3 MB) vs ORT: max logit diff 0.004 / 0.011, argmax agreement 17/17 windows; GPU compute 0.475 ms median. The server itself uses ORT for now (TensorRT arrives with the C++ server).

## Phase 8: decision logic (`server/fallback/decision.py`, pure Python, 20 unit tests)
- Idle gate (strict hand seen in >= 2 of the last 5 frames, else nothing can happen and the EMA resets), EMA smoothing, candidate = best non-`none` class above the threshold, commit after M consecutive agreeing frames, cooldown 800 ms, re-fire protection, word joining within 1500 ms, one event per frame (a second queued event goes out one frame later).
- **Join timer** runs from when the first word stops being predicted, not from its commit: a long sign commits early and would otherwise eat the window.
- **Re-fire protection:** a committed word is "fired" until another word has been predicted for 3 frames, `none` for 8 frames (a sign flickers to `none` mid-way; 3 frames re-fired words), or the gate closes.
- **Sentences:** HOW then YOU -> `how_are_you`; WHERE then YOU or YOU then WHERE -> `where_are_you`. `how`, `where`, `you` wait up to 1.5 s for a partner, so they appear up to 1.5 s late; hello, what, why are immediate. `protocol/labels.json` now has `labels` (7 classes) and `sentences`; `committed_label` may be either; PROTOCOL.md and the conformance test were updated.
- **Fallback server:** real pipeline per frame: JPEG decode -> RTMW (full frame, `training/rtmw_ref.py`) -> `signfeat` -> 30-frame window resampled to 10 fps from the client timestamps (so dropped frames do not stretch time) -> SignNet (ONNX) -> Decision. Profiles `primary` / `fallback` in `server.json`.
- **Known limits:** short signs. Many ASL Citizen signs last 0.5-0.8 s (5-8 frames at 10 fps) and the model's confidence only crosses the threshold in the last 2-3 frames, so they are often missed (the model is conservative: nearly all errors are a real word reported as `none`, almost never one word as another). `where` and `you` (pointing-type signs) are the weakest. A live signer who holds a sign for about a second should do better than the dataset clips.

## Phase 4-6: C++/CUDA server (2026-11-19)
- **Own HTTP/WebSocket layer instead of ixwebsocket.** The protocol needs `GET /health` and an HTTP 401 before the upgrade on one port. ixwebsocket's server handshake (`IXWebSocketHandshake.cpp`, `serverHandshake`) rejects every request without `Sec-WebSocket-Key` with 400 and its HTTP server is a separate class on another port, so neither could be done on port 8765. `server/cpp/src/net.cpp` is ~300 lines of Winsock (RFC 6455: handshake with SHA-1/base64, masked client frames, fragmentation, ping/pong, close, 16 MB drain so a 5 MB message still gets `too_large`). Unit-tested (RFC example hash, message validation) and passes conformance 9/9. `ixwebsocket` stays in `vcpkg.json` only because removing it would force a manifest reinstall; it is not linked.
- **Threading:** one reader thread + one worker thread per connection, one GPU pipeline behind a mutex. Latest-only slot per connection; `dropped_frames` counts replaced waiting frames (same rule as the Python server). Empty end_of_stream sets a reset flag that the worker applies before the next frame.
- **Which parts run on the GPU.** nvJPEG decode, the fused preprocess kernel and the SimCC decode kernel run on the GPU, the keypoint network and SignNet run in TensorRT FP16. Features (57 points, window normalisation, velocities, flags: ~10 kB of data) and the decision logic run on the CPU in C++ (`features.cpp`, `decision.cpp`): they are tiny, and the spec allows "CUDA/C++". The ring of keypoint rows is a CPU deque keyed by client timestamp (needed for the 10 fps resampling the Python server does), not a GPU ring buffer. Only one stream sync per stage (the CPU needs the keypoints, then the logits).
- **Preprocess kernel = rtmw_ref.pose_crop, exactly.** Full-frame box [0,0,w,h], padding 1.25, aspect fixed to the model input, 3-point affine (centre, a point above, its rotation) solved in double like `cv2.getAffineTransform`, bilinear sampling at integer-aligned coordinates (cv2.warpAffine convention, taps outside the frame are 0), rounded to 8 bit (warpAffine output is uint8), BGR->RGB, `(v - mean) / std` with the ImageNet mean/std in 0..255 units. Source: the model's `pipeline.json` as recorded in Phase 3. cv2 interpolates in 1/32-pixel fixed point; the kernel uses exact float weights, so they differ by up to one grey level (unit test bound 2/57 after normalisation, measured against real cv2 output). The affine parameters are computed on the CPU from the image size (no detector, so no ROI round trip exists).
- **SimCC decode kernel:** one block per keypoint, first-maximum tie-breaking like numpy, float32 operations in numpy's order using `__fmul_rn`/`__fadd_rn` (no fused multiply-add) so the results equal `rtmw_ref.simcc_decode`. No `--use_fast_math` anywhere (exact parity was worth more than speed here).
- **Engines:** `server/scripts/build_engines.ps1` builds fixed-shape (batch 1) FP16 keypoint engines from the ONNX files; the temporal engines come from `training/export_onnx.py`. Missing or wrong-version engines fail at startup with the exact rebuild command.
- **Port of the Python logic:** `decision.cpp` is a line-by-line port of `decision.py` (same 20 cases in `tests/test_decision.cpp`); `features.cpp` reproduces `torch.nanmedian` (lower median for even counts) and the loose/strict hand flags. Golden data from the Python code is in `server/cpp/tests/data/golden.json` (regenerate with `tests/gen_golden.py`).
- **Not done (cut for the Nov 28 deadline, per the brief):** CUDA Graph, runtime degrade tiers (tier 1 low-res/small-engine switch, `--mode safe`), tiers 2/3, the zero-allocations-per-frame debug counter (a frame allocates only small host objects: the JPEG copy, JSON), the debug keypoint field for drawing keypoints on the client.

## Hardening round 2 (2026-11-19)
- **Strict network layer, bounded resources.** One deadline for the whole handshake request (a per-read timeout would let a one-byte-per-second trickle hold a thread forever), connection cap 64 (then 503), strict RFC 6455 (masked client frames, no unknown opcodes or reserved bits, no fragmented or oversized control frames, close 1002/1009), nothing above 64 MB is ever read. Chosen because the server is reachable from the internet through the tunnel and every connection costs two threads.
- **ASan for the network tests, not compute-sanitizer:** compute-sanitizer watches CUDA calls only. The network layer was made GPU-free (`IProcessor`, library `signlang_net`) so the same tests run under MSVC AddressSanitizer; a deliberate heap-overflow probe proves ASan is active. compute-sanitizer needs `--launch-timeout 0` on this driver.
- **Degrade is sticky and per profile.** Switching keypoint model changes the feature statistics, so streams restart (window and decision state) on the new profile and that profile's SignNet is used; an automatic return would flap under load. Triggers: sustained slow frames, low VRAM, or an exception in the primary stage.
- **Low-confidence keypoints are not masked per point (training and server alike).** Report in STATUS "Step 2"; a fix changes the feature distribution and needs retraining, deferred until the live-check table.
- **The start/switch scripts read the token from the Windows user variable first** (see STATUS Step 4).

## Same-word guard against double commits (2026-11-20)
- **Root cause was the idle gate flickering, not the probability dipping** (live diag log: p(hello) 0.92-0.97 between the two commits, strict hand presence dropping for several frames, which resets the decision state). So the guard keys on the MODEL (raw p(word) low for 3 frames = the sign ended) and ignores the gate. The user's suggestion "hands down or low motion for ~300 ms" is kept as 3 frames, but measured on the word's probability because hands-down detection is the thing that flickers.
- **Only the most recently committed word is guarded**, so HELLO WHAT HELLO with the hands staying up commits all three; a different word replaces the guard. A time fallback (2 s without the model seeing the word) lets a word through when no clean "rest" happens.
- **Settings were chosen on the live log and checked on VAL/TEST**, because the dataset clips contain almost no doubles; insensitive: n=1..5 and p=0.1..0.5 all remove every flat double. Chosen n=3 (300 ms, as asked), p<0.2, 2000 ms. n=1-2 would keep one more quick YOU repeat (see STATUS "Known cost").
- **No gate hysteresis, no threshold or model changes** (smallest safe change, same code in both servers). Evaluation streams now use a 3.5 s tail (`double_commit_report.py --tail`) because a 2 s tail hides emissions of held words; `replay_eval.py` keeps 2 s for continuity with the published numbers.
- The existing cooldown unit test runs with the guard off (it is about the generic cooldown); the guard has its own 15 tests per implementation plus a frame-by-frame C++/Python golden test.

## Tracking at the send rate, recognition at exactly 10 fps (2026-11-20)
- **Why a tick clock instead of "run everything on every frame":** the decision settings and the model's 3 s window are defined in 100 ms frames (M, gate, cooldown in ms, `repeat_rest_frames`). At 30 fps they would triple in speed. Keypoints are the only part that gains from more frames, so only they run per frame. No retraining and no threshold change were needed; the dataset replay at 20 and 30 fps matches 10 fps within noise.
- **Closest frame by client timestamp, causal:** a tick fires on the first frame at most half a measured frame interval before it, and uses the closer of that frame and the previous one. A fixed tolerance either delayed ticks by a whole frame at 10 fps (small) or accepted frames 50 ms off at 30 fps (large); the running interval estimate gets both right (first interval seeds it: a 100 ms default made the first ticks at 30 fps inaccurate, found by a test).
- **Gaps:** missed ticks hold the nearest frame and only the last 3 run the model (catch-up cost bounded); a pause over 5 s restarts the grid.
- **Committed words are queued, one per reply;** between ticks the reply repeats the newest label/state (never "committed").
- **Client sends on camera frames, not on a timer;** the timestamp is the capture time. Default 20 fps pending the laptop sweep; the flow control limit (3 in flight) is unchanged, it caps the rate at 3 / round trip.
- **The overlay smoothing already existed** and stays drawing-only.

## False triggers: per-word threshold only (2026-11-21)
Live false commits (typing, resting, waving in view) are high-confidence, 2-6 s, still-hand predictions, so global threshold, margin, minimum duration, onset-rest, two-handed
rules and gate hysteresis were tested and rejected: they cost words or sentences for little or no live gain (table in STATUS). Adopted: a per-word threshold, `thr_why` 0.7 (free on VAL and TEST,
both keypoint models). Seed ensemble rejected for now (sentences -4 on TEST). The temporary guard knobs were removed from decision.py so Python and C++ stay a line-by-line pair.

## Motion gate (2026-11-21)
Live false commits are held still hands, so the next guard uses a feature the decision did not have: hand motion between ticks in shoulder widths, summed over a short window and required before any commit (so also for every word of a sentence).
Motion is computed from the tick rows the temporal model already uses (no extra model, no retraining), identically in Python and C++ (golden test). The gate ships OFF until its threshold is chosen on the user's live log; the dataset only bounds it from above (W20 / 1.3 costs <= 1 word and 1 sentence).
